## 1. 产品概述

### 1.1 一句话定位

把**老板、订单、每日打卡和收款**放进同一本小账本 —— 面向个人游戏代肝接单者的离线记录工具。

### 1.2 要解决的问题

接单量上升后，代肝从业者最容易混在一起的是四件事：

1. 今天该上哪个号，还有哪些号没做
2. 这单做到哪一天了，漏打卡怎么补
3. 老板付了多少，还欠多少
4. 换手机 / 怕忘记，数据怎么带走

传统做法是聊天记录 + 备忘录 + 表格三者拼凑，导致"做到哪天"和"收了多少"经常对不上。

### 1.3 核心价值

- **一条链路打通**：老板 → 游戏账号 → 订单 → 任务打卡 → 收款，缺一环的记录工具没有意义
- **纯离线**：不申请网络权限，不需注册，不上传任何业务资料
- **轻量**：单兵工具的体量，不照搬大型 SaaS 的模块体系
- **账实分离**：约定价格与实际收款分别记录，任务完成与收款状态互不干扰

### 1.4 价值主张

> 游戏操作你自己做，任务、进度和账目交给本子。

## 2. 目标用户与场景

### 2.1 目标用户

| 画像 | 特征 | 核心诉求 |
|---|---|---|
| **主用户** | 个人游戏代肝从业者，1 人接单，同时服务若干老板 | 今天该做什么、谁欠我钱、做到哪天了 |
| 次要用户 | 兼职接单的玩家/学生 | 轻量、不想学复杂工具、随手能记 |

### 2.2 典型使用场景

| 编号 | 场景 | 触发 | 期望结果 |
|---|---|---|---|
| S-1 | 每日开工 | 早上 | 打开「今日事项」，看到今天要上的号和要做的任务，逐项勾选 |
| S-2 | 集中补作业 | 隔了几天 | 「补录 / 更正」选历史日期补打卡，归属仍是原游戏日 |
| S-3 | 催款 | 月底 | 「数据统计」看待收列表，定位欠款订单 |
| S-4 | 收到转账 | 随时 | 订单详情记一笔实收，支持分次 |
| S-5 | 老板续期 | 托管到期 | 续期，旧期次价格/打卡/收款全部保留 |
| S-6 | 换手机 | 换机前 | 导出加密备份，新机导入恢复，含截图 |
| S-7 | 新游戏接单 | 第一次 | 建单时选模板预填任务，不用手打 |

### 2.3 非目标用户

工作室团队（需要协作与权限）、希望 App 代打游戏的用户、需要接单平台的流量型用户。

## 3. 范围

### 3.1 本期范围（v1.6 已实现）

今日事项打卡、老板与游戏账号管理、托管/短期订单、任务周期与补录、收款与欠款、
数据统计、游戏模板库、三类本地提醒、完整备份与恢复、归档管理。

### 3.2 明确不做（范围外）

| 不做项 | 原因 |
|---|---|
| 注册 / 登录 / 账号体系 | 单机工具，无服务端 |
| 云同步 / 多端实时协作 | 离线优先，同步会引入冲突与隐私成本 |
| 自动代打、代肝脚本 | 与记录工具定位不符，且有平台合规风险 |
| 交易平台 / 支付网关 / 托管平台 | 只记录，不撮合交易 |
| 模板在线商店 | v1.6 仅支持本地文件导入导出 |
| 托管暂停 / 中途转单 | 状态机复杂度高，v1.6 未建模 |
| 应用锁 / 指纹 / 二次身份验证 | 本机数据由用户自行管理访问权限 |
| iOS 版本 | 当前仅 Android |

> 范围外项不排除未来版本纳入，但纳入任一项都需要重做数据模型与隐私策略。

## 4. 核心概念与信息架构

### 4.1 领域概念

| 概念 | 说明 | 关键约束 |
|---|---|---|
| 老板 Owner | 客户。固定自动编号 + 可改昵称 | 编号不随昵称变化、不回收 |
| 游戏账号 GameAccount | 老板名下的游戏身份 | 游戏、区服、UID、登录账号、登录方式、密码 |
| 订单 Order | 一次服务委托 | 托管（HOSTING）或短期（SHORT_TASK） |
| 托管期次 HostingPeriod | 托管单的计费与打卡单元 | 价格属于期次；续期递增 `periodIndex` |
| 任务定义 TaskDefinition | 订单上的一条任务配置 | 一次性/每日/每周/指定星期/每隔 N 天/每月固定日号 |
| 发生记录 Occurrence | 托管任务在某次应做窗口的记录 | 稳定键 + 唯一索引 |
| 实收 Receipt | 实际收到的一笔钱 | 只来自用户输入，绝不从价格或完成状态推算 |
| 游戏模板 GameTemplate | 建单时的默认值来源 | 订单创建时快照，改模板不影响已有订单 |
| 附件 Attachment | 任务或打卡的截图 | 存应用私有目录，库中只存引用 |

### 4.2 信息架构

```
底部导航（3）
├── 今日事项
│   ├── 托管打卡分组 / 短期任务分组
│   └── 整单完成 · 全部完成 · 批量撤销 · 数值进度 · 展开已完成
├── 账号信息
│   ├── 老板列表（进行中置顶 / 高亮）
│   ├── 老板详情
│   │   ├── 游戏账号列表（已归档默认折叠）
│   │   └── 订单列表 → 订单详情
│   └── 已归档记录
└── 数据统计
    ├── 本月 / 全部累计
    ├── 实收趋势 · 累计实收 · 全部待收
    └── 本月/累计接单构成

右上角设置（独立页，4 个子页）
├── 收款明细
├── 游戏模板（库 → 编辑器 / 导入 / 导出）
├── 提醒设置（3 类开关 + 时间）
└── 备份与恢复（导出 / 恢复）

订单详情（二级下钻）
├── 托管打卡日历
├── 期次与往期记录
├── 任务打卡 + 截图
├── 收款区（分次收款 / 更正 / 作废）
├── 管理 → 修改日期 · 续期 · 删除或作废
└── 补录 / 更正（历史日期）
```

**导航原则**

- 新增订单入口**始终处在老板上下文**内（老板详情 → 账号 → 「为这个账号接新单」），不设全局新建入口
- 设置页及子页不显示底部导航
- 设置页与统计页提供跳转入口（统计页跳设置、模板空态跳「设置 → 游戏模板」）

## 5. 功能需求

优先级：**P0** 核心不可缺 · **P1** 重要 · **P2** 可延后

### FR-1 今日事项（P0）

**FR-1.1** 进入「今日事项」默认展示**托管打卡**分组与**短期任务**分组，两组可随时切换。

**FR-1.2** 托管单按订单聚合展示：游戏名 · 区服、订单名称、本期期限、今日应做任务清单。

**FR-1.3** 「应做任务」依据**游戏日**与订单的周期/刷新规则计算，不按手机自然日零点硬切。
- 托管尚未开始 → 显示「托管尚未开始，不会提前生成任务」
- 托管已到期 → 显示「已到期 · 待续期」，不再生成新任务，但保留历史、截图与期次价格

**FR-1.4** 任务完成方式：
- **单项勾选**：完成 / 取消完成
- **整单完成**：完成当前订单本期所有应做任务
- **所有应做托管单完成**：跨订单一次性完成

**FR-1.5** 批量完成**可撤销**：
- 撤销恢复此前状态，**不能清除原本已完成的项**
- 撤销结果以弹窗呈现，明示"以下项目在批量完成后又被修改，已保留最新结果"
- 已被撤销过的批次不可重复撤销

**FR-1.6** 数值型任务（`NUMERIC`）提供独立的进度输入，展示起始值 / 当前值 / 目标值 / 单位；「未填写」需显式提示。

**FR-1.7** 短期单页展示**所有未完成**短期任务，排序：逾期优先 → 按截止时间升序 → 无期限放最后。

**FR-1.8** 全部完成的托管订单移至底部**「已完成」折叠区**，可展开/收起；未全部完成的仍在待办区。

**FR-1.9** 单条订单卡片可直达订单详情。

### FR-2 老板与游戏账号（P0）

**FR-2.1** 老板列表以卡片分组展示，自动编号 + 昵称。

**FR-2.2** **进行中状态标识**（v1.5）：有未完成订单的老板显示图标、进行中订单数、高亮边框，并**自动置顶**；最后一单结单或托管服务到期后，自动恢复按老板编号排序。

**FR-2.3** 老板列表顶部仅提供「**新增**」（新增老板）；进入老板详情后才可新增游戏账号、接新单。

**FR-2.4** 老板详情展示其名下多个游戏账号及各自订单；一个老板可有多个账号，一笔订单仅关联一个账号；同一账号可同时有托管单和短期单，也可多次接单。

**FR-2.5** 游戏账号字段：游戏名、区服、UID、登录账号、登录方式（密码 / 验证码）、密码（仅密码登录时）。

**FR-2.6** 登录信息默认遮蔽，提供「展开登录信息」；UID、登录账号、密码支持**一键复制**并给出「已复制」反馈。**查看和复制凭据不设置额外身份验证门槛**（单机工具定位）。

**FR-2.7** 验证码登录**不保存验证码**。

### FR-3 订单管理（P0）

**FR-3.1** 两种订单类型，字段与语义不同：

| | 托管单 | 短期单 |
|---|---|---|
| 适用 | 连续多天的日常服务 | 活动、关卡等一次性委托 |
| 期限 | 开始日期 + 到期日期（首尾均含，开始日计为第 1 天） | 交付期限（选填） |
| 任务 | 仅周期任务 | 一次性或周期任务均可 |
| 价格 | 挂在**期次**上 | 挂在**订单**上（整单总价） |
| 续期 | 支持 | 不需要 |

**FR-3.2** 新增订单页流程：老板固定 → 选游戏账号 → 选订单类型 → 配置任务与期限 → 配置价格与收款 → 可选首笔实收 → 提交前核对。

**FR-3.3** 周期任务支持：每日、每周（指定星期 + 刷新时刻）、指定星期、每隔若干天（从托管开始日算起）、**每月固定日号（1–31，当月无该日则跳过）**。

**FR-3.4** 每日刷新时间可配置（HH:mm），决定**游戏日**的起点。预置时区含**中国时间**与**美国东部纽约时间**（正确处理夏令时）；时区列表可增删，模板与建单共用同一列表。

**FR-3.5** 游戏模板（选填）用于预填任务、时区与刷新时间；不选模板时模板库为空需给出明确引导。

**FR-3.6** 建单支持**同时录入首笔实收**：金额、实际到账时间（默认现在，可补记过去）、渠道、备注（仅"其他"渠道）。

**FR-3.7** 收款方式分**一次结清**与**分批收款**：
- 一次结清：首笔实收需与约定价格一致
- 分批收款：允许首笔小于约定价，其余留待收
- 「关闭时订单保持未收款，可稍后在详情中记录」

**FR-3.8** 建单幂等：提交后**不会再次建单**（同一次操作重试返回原订单），并提供「再建一张」明确开新单。

**FR-3.9** 订单详情展示：本期、期限、状态、任务打卡、收款记录、往期记录。

**FR-3.10 续期**：
- 用户**主动**触发，到期后显示「查看并续期」
- 沿用原订单标识（`orders` 行数**不增加**），从**操作当天**开始
- 新建本期期限、价格、打卡与收款；沿用原任务配置
- 本期实收从零开始，上期记录归历史，**所有未清欠款延续**
- 新期次起始日按该期存储时区的游戏日期计算

**FR-3.11 修改服务日期**（v1.6）：
- 入口在订单详情右上角「管理 → 修改日期」
- 托管单可选期次；短期单可修改或**清除**截止日期
- 已有发生记录的期次**锁定开始日期**；结束日期不能排除已有记录
- 拒绝期次重叠、先后顺序颠倒
- **不改写**价格、收款、附件与历史打卡归属

**FR-3.12 删除 / 作废订单**（v1.6）：
- **无业务记录**的误建订单 → 确认后**删除**
- **已有打卡 / 附件 / 收款**的订单 → 只能**作废**
- 作废：保留历史与实际收款，取消剩余待收、任务、提醒与有效接单计数；已有收款可继续更正或作废
- 删除与作废**不可撤销**，确认框必须明确提示

### FR-4 任务打卡与补录（P0）

**FR-4.1** 托管单详情提供**打卡日历**，直观展示每天的打卡状态。

**FR-4.2** 截图：任务完成记录可**添加、查看、替换、删除**截图；截图归属具体的任务或某次打卡记录。

**FR-4.3** 补录入口「补录 / 更正」：
- 可选范围：**本期开始日 ~ 今天（含今天）**的游戏日期；未来日期不可补录
- 补录**同时保存**归属的游戏日期/游戏周、实际记录时间，并**标记为补录**
- 所选日期不在任务重复周期内、或该期未配置任务 → 明确拒绝并说明原因
- 托管期次尚未开始 → 期次只读，不可补录
- 每周任务按**游戏周**归属，同一周内选任意日期都指向同一条记录，不按天复制

**FR-4.4** 批量完成**不补历史遗漏**（今日页明示"所有托管单完成不会补写历史遗漏"）。

### FR-5 收款与账务（P0）

**FR-5.1** **约定价格与实际收款分别记录**，互不推算。

**FR-5.2** 收款字段：金额、**实际到账时间**、渠道、备注（仅"其他"）、所属订单与期次。

**FR-5.3** 支持一次结清与分批收款；每笔实收由用户**选择所属期次**，不自动抵扣最早欠款。

**FR-5.4** 渠道：微信、支付宝、银行卡、现金、其他。

**FR-5.5** 收款**更正**不删除原记录：
- **改金额 / 改时间 / 改渠道**（AMEND）→ 插入新记录，原记录置为「已更正」
- **作废**（VOID）→ 原记录置为「已作废」
- 历史永久可读，收款明细页展示「已更正为 ¥X」「已作废，不计入实收与欠款余额」

**FR-5.6** 待收 = `max(0, 约定价 − 实收)`；只有待收 > 0 才进入待收列表；收齐后自动移出。

**FR-5.7** 归档、已完成、已到期订单的欠款**仍可收取**（但工作写入被归档守卫拒绝）。

**FR-5.8** 「收款明细」页：全部实收流水按**实际收款时间倒序**，展示金额、渠道、备注、老板 / 账号 / 订单 / 归属期次。

### FR-6 数据统计（P0）

**FR-6.1** 时间范围切换：**本月** / **全部累计**。

**FR-6.2** 实收按**实际收款时间**统计；接单量按**建单时间**统计，**续期不增加订单数量**。

**FR-6.3** 指标卡：累计实收 / 本月实收、全部待收（待收款列表）、本月接单 / 累计接单、接单构成（托管 vs 短期占比）。

**FR-6.4** 实收趋势柱状图：本月视图按**周分段**统计，全部累计视图统计**最近六个自然月**。

**FR-6.5** **全部待收与待收款列表始终包含所有当前欠款，不受本月 / 累计筛选限制**。

**FR-6.6** 历史收款流水不在本页展开，入口在「设置 → 收款明细」。

### FR-7 游戏模板（P1）

**FR-7.1** 模板包含：游戏名称、模板版本、游戏版本备注、时区、每日刷新时间、每周刷新规则、分类、任务列表（标题、进度方式、默认数值与单位、默认重复周期）。

**FR-7.2** 内置**通用模板**开箱可用；用户可新建、编辑、删除自有模板。

**FR-7.3** 支持**文件导入 / 导出**（JSON）供社区分享；**无在线商店**。

**FR-7.4** 模板是**创建时的默认值**，订单创建时把任务、刷新规则、模板来源**快照**进自己的记录；**没有任何业务表通过外键引用模板**。

**FR-7.5** 因此：编辑 / 替换 / 删除模板，**不产生**针对订单、期次、发生记录、收款、附件的任何写操作。删除模板会清空账号的默认模板，历史订单的模板来源列保持为快照文本。

**FR-7.6** 模板中的**一次性任务只适用于短期单**；托管订单创建时只取周期任务，若模板没有周期任务则明确提示，不静默改写。

**FR-7.7** 用户删除内置模板后**不会在下次启动复活**。

### FR-8 提醒（P1）

**FR-8.1** 三个**独立**开关与时间配置，初始全部关闭：

| 类别 | 触发条件 |
|---|---|
| 短期截止 | 游戏日已到或超过截止日且订单未完成；未设期限不提醒 |
| 托管到期 | 仅最新期次的最后一个游戏日提醒，到期后停止；续期后用新期次快照 |
| 未完成 | 当前仍有效期次中当前发生槽未完成的托管任务，以及未完成短期任务 |

**FR-8.2** 每类别**每个手机本地日最多提醒一次**，投递记录存本地用于去重。

**FR-8.3** 时间是**手机本地时间**；业务是否应提醒用订单保存的**游戏时区 + 每日/每周刷新规则**判定。

**FR-8.4** 归档老板 / 账号**不提醒**；历史补录不抵扣今天的未完成资格，撤销完成后恢复资格。

**FR-8.5** Android 13+ 开启开关时**请求通知权限**；拒绝后设置仍保存，其他业务可继续，页面提供「前往系统设置」并在回到页面时刷新状态。

**FR-8.6** 通知**不包含**账号登录名、密码或验证码；锁屏采用 `private` 可见性。单订单通知打开订单详情，汇总通知打开今日事项。

**FR-8.7** 当天时间已过之后才打开开关或修改时间，从**下一次**配置时刻开始，不立即补发。

### FR-9 备份与恢复（P0）

**FR-9.1** 备份文件后缀 `.dgbk`，经系统文件选择器读写，**不需要广泛存储权限**。

**FR-9.2** **密码可选**：
- 留空 → 普通 ZIP 归档
- 填写并二次确认 → **AES-256-GCM 加密信封**（PBKDF2-HMAC-SHA256，21 万次迭代，每次重新生成盐与 nonce）
- 恢复时仅加密文件要求输入密码

**FR-9.3** 备份内容：18 张持久业务表 —— 老板及编号计数器、游戏账号（含登录凭据）、模板/分类/任务/种子状态、批量完成及撤销明细、订单/托管期次/任务定义/发生记录、截图引用、收款/更正历史/建单幂等记录、提醒设置；**附件文件内容一并打包**。

**FR-9.4** **不导出**两表：`app_settings`（本机身份与恢复提交标记，恢复时产生新身份）、`reminder_deliveries`（本机通知去重状态，恢复时清空）。

**FR-9.5** 恢复流程：校验文件完整性与版本 → **隔离的真实 Room 验证**结构、枚举、外键、业务归属、有效收款上限与 SQLite 完整性 → 展示**备份摘要**（老板/账号/订单/实收/附件/记录数、导出时间）→ 用户**明确确认** → 整库替换。

**FR-9.6** 恢复**不做隐式合并**；密码错误、附件缺失、文件损坏**不修改现有资料**。

**FR-9.7** 恢复为**整库替换**，会**清空当前数据**，因此必须先展示摘要并二次确认。

**FR-9.8** 兼容：schema 8 备份可恢复 schema 8 与上一版 schema 7 备份（仅补齐 3 个 NULL 列）。其他 schema、未知格式或信封版本在**替换前**拒绝。schema 8 备份**不能**在旧版应用恢复。

### FR-10 归档管理（P1）

**FR-10.1** 归档老板：老板及其当时未归档的账号共享同一 `archiveBatchId`；已归档状态在列表中可见，移入「归档记录」页。

**FR-10.2** 恢复老板：**只恢复同批次账号**；独立归档的账号保持归档，需单独恢复。

**FR-10.3** 重复归档 / 恢复**幂等**，不重写时间戳或批次。

**FR-10.4** 老板归档期间，其账号的写入**一律拒绝**；归档后资料不删除，可随时恢复。

**FR-10.5** 归档守卫：归档老板 / 账号要求**没有未完成短期单**且**没有未到期托管期**。

**FR-10.6** 老板详情中**已归档账号默认折叠**（v1.6），可展开查看及恢复，**展开状态按老板保存**。

## 6. 关键业务规则

### BR-1 游戏日与刷新（最容易出错的地基）

三个概念严格区分：

1. **本地日历日期** —— 存储时区中的民用日期，日期选择器使用
2. **游戏日期** —— 以「每日刷新时间」为起点的一天。当前本地时间早于刷新点时，游戏日期为**前一天**
3. **每周发生窗口** —— `[配置星期 + 配置时间的刷新时刻, +7 天)`。周任务每窗口**恰好一条**记录，窗口可跨多个游戏日但**不按天复制**；展示日期为起始日与起始日 +6 天

每日、指定星期、每隔 N 天、每月固定日号任务均归属**游戏日期**。

**所有任务只在 `[startDate, endDate]` 内存在**：未来开始日不生成工作，到期日后不再生成新任务。

### BR-2 发生记录稳定键

| 周期 | 键格式 | 归属日期 |
|---|---|---|
| 每日 | `D:<gameDate>` | 当天游戏日 |
| 指定星期 / 每月固定日号 | `S:<gameDate>` | 当天游戏日 |
| 每隔 N 天 | `E:<gameDate>` | 从期次 `startDate` 起第 `k×N` 天 |
| 每周 | `W:<windowStartLocalDate>` | 窗口起始日（展示时裁剪到托管期） |

唯一索引 `(taskDefinitionId, occurrenceKey)` 是重复生成与重复点击的**最终防线**。

周任务窗口与托管期次只部分重叠时仍保留一条记录，但键使用**未裁剪**的窗口起始日，保证同一窗口在期次两端稳定。

### BR-3 幂等与并发

所有写操作是**命令**，带 `operationId` 幂等键 + 规范化请求指纹：

| 命令 | 幂等键 | 相同重试 | 冲突载荷 |
|---|---|---|---|
| 建单（含首笔） | `order_creation_operations.operationId` | 返回原订单/原收款 | 拒绝 |
| 收款 | `receipts.operationId` | 返回原收款 | 拒绝 |
| 更正 | `receipt_corrections.operationId` | 返回原审计，历史不增行 | 拒绝（含不同 `reason`） |
| 续期 | `hosting_periods.renewalOperationId` | 返回原期次 | 拒绝 |
| 批量完成 | `completion_batches.operationId` | 返回原批次 | 拒绝 |

并发相同命令由唯一索引兜底，落败事务回滚后读取获胜事务的已提交结果。

### BR-4 账务口径

- 只有 `status = ACTIVE` 的收款计入实收；`REPLACED` / `VOIDED` 计 0
- 短期单：一件应收 = 订单 `priceCents`，`paid = Σ ACTIVE receipts(periodId IS NULL)`
- 托管单：**每期**一件应收 = 该期 `priceCents`，`paid = Σ ACTIVE receipts(periodId = 该期)`
- `outstanding = max(0, price − paid)`；**欠款是全时段未收金额，不受月份筛选影响**
- 实收统计按 `receivedAt` 落在报表时区窗口内汇总
- 金额一律**整数分**（`priceCents`），不存在浮点金额
- `receivedAt` 是**实际到账**时间，允许历史值；`createdAt` 是录入时间，两者**明确分离**
- **订单状态与付款状态分离**：任务完成与收款状态互不影响，完成未收齐仍可追款

### BR-5 备份安全边界

- 归档上限 512 MiB；清单 1 MiB；数据 JSON 64 MiB；条目 5000；附件 2000；单图 32 MiB；附件总计 384 MiB
- 超过 8 MiB 的解压内容限制压缩比 200
- 禁止绝对路径、目录、路径穿越、分隔符嵌入、未知条目、重复条目、未登记或缺少的附件
- 附件清单与数据行的路径、编号、MIME、大小须相符，全部校验和必须匹配
- JSON 深度、精确表 / 列集合与值类型均限制
- SHA-256 用于发现损坏；普通归档的校验和不提供对抗主动修改的认证，需密码保护时使用 GCM 信封
- 密码数组与派生字节使用后擦除，**不记录秘密日志**

## 9. 已知限制与风险

| 编号 | 限制 / 风险 | 当前处理 |
|---|---|---|
| L-1 | 主要在 **Android 模拟器**验证，实体机兼容性待用户测试 | README 明确告知；建议先少量演示记录熟悉流程 |

## 11. 术语表

| 术语 | 释义 |
|---|---|
| 老板 | 客户账号，自动编号、昵称可改 |
| 期次 | 托管单的计费与打卡单元，价格属于期次 |
| 游戏日 | 以每日刷新时间为起点的一天，与手机自然日可能相差一天 |

| 待收 | 约定价减实收，全时段口径 |
| 作废 | 有记录的订单的停用方式，保留历史与实收 |
| 快照 | 订单创建时复制模板/规则的独立副本，之后互不影响 |
| DatasetGate | 跨数据库与通知的数据集共享许可，防止恢复中途换数 |
